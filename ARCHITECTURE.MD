# Архитектура проекта CheckIn

## 1. Общая архитектура

CheckIn построен по клиент-серверной архитектуре.

Система состоит из следующих основных контейнеров:

- **Web Client** — веб-интерфейс системы;
- **Backend Service** — REST API и бизнес-логика;
- **Database** — PostgreSQL, хранение основных данных;
- **File Storage** — хранение документов и файлов, прикрепляемых к объяснениям отсутствия.

Пользователи взаимодействуют с системой через Web Client. Web Client отправляет запросы в Backend Service по REST API. Backend Service выполняет бизнес-логику, проверяет права доступа и взаимодействует с PostgreSQL и файловым хранилищем.

---

## 2. Пользователи системы

В системе предусмотрено пять основных ролей:

- **Студент** — отмечает посещаемость через QR-код и предоставляет объяснения отсутствия;
- **Староста** — может вручную отмечать посещаемость группы, если QR-код невозможно использовать или студент пришёл позднее;
- **Преподаватель** — создаёт занятия и QR-сессии, контролирует посещаемость и проверяет объяснения;
- **Куратор** — контролирует посещаемость закреплённых групп и получает уведомления о низкой посещаемости;
- **Декан** — получает сводные данные и формирует отчёты.

## 3. Use Cases

### UC-01. Отметка посещаемости через QR-код

**Актор:** Студент

**Предусловия:**

- студент авторизован;
- преподаватель создал занятие;
- QR-сессия активна.

**Основной сценарий:**

1. Преподаватель создаёт занятие.
2. Система создаёт QR-сессию.
3. Преподаватель отображает QR-код.
4. Студент сканирует QR-код.
5. Backend проверяет действительность QR-сессии.
6. Система создаёт запись посещаемости.
7. В записи сохраняются студент, занятие, способ отметки и время.
8. Посещаемость отображается в системе.

**Результат:** Студент отмечен как присутствующий.

---

### UC-02. Ручная отметка посещаемости

**Актор:** Староста

**Предусловия:**

- староста авторизован;
- занятие существует;
- QR-код невозможно использовать либо требуется отметить опоздавшего студента.

**Основной сценарий:**

1. Староста открывает список группы.
2. Система отображает студентов группы.
3. Староста отмечает присутствующего студента.
4. При необходимости указывает статус опоздания или отсутствия.
5. Система сохраняет запись посещаемости.
6. В записи сохраняется способ отметки `manual`.
7. В поле `marked_by` сохраняется пользователь, выполнивший отметку.

**Результат:** Посещаемость группы сохранена с указанием автора отметки.

---

### UC-03. Добавление объяснения отсутствия

**Актор:** Студент

**Предусловия:**

- студент авторизован;
- занятие существует.

**Основной сценарий:**

1. Студент открывает список пропусков.
2. Выбирает занятие.
3. Выбирает тип причины.
4. Добавляет описание.
5. При необходимости загружает документ.
6. Система создаёт объяснение со статусом `pending`.
7. Преподаватель получает информацию о новом объяснении.

**Результат:** Объяснение отправлено преподавателю.

---

### UC-04. Проверка объяснения

**Актор:** Преподаватель

**Предусловия:**

- преподаватель авторизован;
- существует объяснение со статусом `pending`.

**Основной сценарий:**

1. Преподаватель открывает список объяснений.
2. Выбирает объяснение студента.
3. Просматривает текст причины.
4. Просматривает прикреплённые документы.
5. При необходимости добавляет комментарий.
6. Принимает или отклоняет объяснение.
7. Система сохраняет результат проверки.
8. Студент получает уведомление о результате.

**Результат:** Объяснение получает статус `accepted` или `rejected`.

---

### UC-05. Контроль посещаемости куратором

**Актор:** Куратор

**Предусловия:**

- куратор авторизован;
- у куратора есть закреплённые группы.

**Основной сценарий:**

1. Куратор открывает список закреплённых групп.
2. Система рассчитывает показатели посещаемости.
3. При обнаружении низкой посещаемости создаётся уведомление.
4. Куратор открывает уведомление.
5. Просматривает проблемную группу или студента.

**Результат:** Куратор получает актуальную информацию о проблемах с посещаемостью.

---

### UC-06. Формирование отчёта

**Актор:** Декан

**Предусловия:**

- декан авторизован.

**Основной сценарий:**

1. Декан выбирает факультет.
2. Выбирает кафедру, группу или предмет.
3. Система получает данные о посещаемости.
4. Система рассчитывает показатели.
5. Формируется отчёт.
6. Декан может просмотреть или сохранить отчёт.

**Результат:** Получен сводный отчёт по посещаемости.

## 5. Основные сущности системы

В базе данных используются, в частности, следующие сущности:

1. `users` — пользователи системы;
2. `roles` — роли пользователей;
3. `groups` — учебные группы;
4. `students` — данные студентов;
5. `lessons` — занятия;
6. `qr_sessions` — QR-сессии;
7. `attendance` — записи посещаемости;
8. `explanations` — объяснения отсутствия;
9. `files` — прикреплённые документы;
10. `notifications` — уведомления.

Связи между сущностями проектируются с учётом нормализации данных до третьей нормальной формы (3NF).
